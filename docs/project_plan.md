# 项目实施计划与阶段门槛

## 阶段 1：文献、研究设计与数学模型（已完成）

产物：结构化文献综述、研究设计、数学模型、算法与实验初稿、配置骨架、环境检查和阶段自检。门槛：5 篇论文均有明确用途与不复用边界；预算可识别性、FIFO、不可行补救和热启动精确性已书面处理。

## 阶段 2：确定性与固定储备模型

实现 `scenario_generator.py`、`inventory_model.py` 与配置读取；完成平均场景、`R=0` 和固定比例模型。门槛：库存流、两类预算、固定种子与极端实例测试通过。

## 阶段 3：全场景内生储备扩展式

实现 `extensive_model.py`，在 4 期、20 场景上求解。门槛：所有场景补救可行性与预算检查通过；固定比例中的最好结果不优于内生模型超过容差。

## 阶段 4：标准 C&CG

实现 `recourse_model.py` 与 `ccg.py`，保存逐迭代 LB/UB/gap 和时间。门槛：小规模扩展式与 C&CG 目标一致；重复场景、不可行补救、超时和最大迭代均有明确状态。

实施记录：PR #1 同时交付了阶段3扩展式和阶段4标准 C&CG，虽然当时文件名与 handoff 统一标为“Phase 3”。该历史标签不改变本计划的阶段定义；SPW-C&CG 仍为阶段5。

## 阶段 5：SPW-C&CG

实现 `scenario_pool_ccg.py`，按预算升序建立热启动池。门槛：所有预算下冷/热目标一致；分别报告场景池与变量 warm start；场景池构造时间计入总时间。

## 阶段 6：正式实验与图表

实现 `experiments.py` 与 `plotting.py`，输出 CSV、日志、解和论文图。门槛：训练/测试数据独立；配置、种子和版本完整；失败运行可追踪。

## 阶段 7：文档-代码一致性收尾

从实现反向更新所有公式、伪代码和运行命令，执行完整测试。门槛：README 从干净环境可复现；模型符号与代码字段一一对应；无占位结果或未解释参数。

## 阶段依赖与版本控制

- 自 2026-07-28 起，所有阶段统一采用 Gurobi 13.0.2；配置和运行时
  禁止其他求解器及静默回退。历史 HiGHS 结果仅作为既有验证证据，
  不进入后续正式性能统计。
- 阶段 3 必须复用阶段 2 已通过测试的库存流模块，不另写一套场景库存方程。
- 阶段 4 的补救模型必须与扩展式调用同一约束构造函数，防止两个模型在库龄、容量或成本口径上漂移。
- 阶段 5 只改变初始场景集合与跨预算编排，不改动标准 C&CG 的最坏场景 oracle 和终止条件。
- 阶段 6 的每张表和图都必须能追溯到原始结果 CSV、配置快照、随机种子和代码版本。

每个阶段单独形成可运行提交点。配置字段变更时同步更新样例配置、数据类、README 和相关测试；不得只修改文档或只修改代码。

## 失败与停止规则

- 求解器报告不可行、无界、数值错误或超时时，保留日志和配置，不把该运行纳入正常统计。
- C&CG 若出现“最坏场景已在主问题但 gap 仍超限”，按数值停滞处理，检查主问题目标、补救成本计算和容差，不静默继续。
- 扩展式与 C&CG 不一致时停止进入下一阶段，先在 1 物资、2-4 期和少量手工场景上定位差异。
- 冷启动与热启动目标不一致时，SPW-C&CG 不得进入性能实验。
- 若正式规模超出时间或内存预算，先报告可验证的最大规模，再考虑并行补救、场景池裁剪或连续不确定集扩展。

## 最终交付定义

项目完成不以“代码能够启动”为标准，而以以下证据同时存在为标准：核心测试通过；小规模三种算法目标一致；固定/内生储备比较可复现；样本外结果文件完整；图表可由脚本重新生成；README 在新环境中给出从安装、生成数据、测试到运行实验的连续命令。
